Refactor the handler in `server.ts` per Pattern 3. Extract a `generateOnce()` helper that calls `ai.models.generateContent(...)`, then: reads `response.candidates?.[0]?.finishReason` FIRST (before `.text`, per Pitfall 3 — `.text` is undefined on safety blocks); if finishReason is present and not STOP, returns a failure result carrying the reason and a `retryable` flag where retryable = reason is not in the hard-fail set {SAFETY, RECITATION}. If finishReason is STOP (or absent) read `response.text`; if falsy return failure reason EMPTY (retryable). Guard `JSON.parse` in try/catch; on throw return failure reason PARSE (retryable). Run `GeneratedContentSchema.safeParse`; on failure return reason SCHEMA (NOT retryable). On success return the validated data.

Handler flow: call `generateOnce()`; if it fails and `retryable` is true, call `generateOnce()` a second time (single retry only, no more; a small optional 200-500ms delay is acceptable but not required — no backoff library). Map the final reason to a clear Vietnamese, human-readable message (no stack, no raw JSON, no error.message) and return it with an appropriate status (>=400). Wire it through the existing shape `res.status(code).json({ error: <vietnamese> })` so the existing `useStore.error` → red banner path in `App.tsx` renders it unchanged. Log the technical detail server-side via `console.error` only. Never retry SAFETY / RECITATION / SCHEMA (deterministic; Anti-Pattern). Keep the happy path from Plan 01 intact.
